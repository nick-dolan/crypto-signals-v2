# Правила для агентов

Строим систему раннего предупреждения, которая для каждой монеты оценивает: вероятность сильного движения в ближайшем будущем. 

Описание какие данные нам доступны здесь: `docs/Данные TradingView.md`

## Краткость — для ответов и всей документации

- По умолчанию пиши только суть. Подробности — по прямому запросу или если без них нельзя принять решение.
- Обзор описывает назначение, а не реализацию, оформление или историю изменений.
- `README.md`: только перечисленные шаги, по одной короткой фразе о назначении. Без параметров и подробностей.
- `docs/План.md`: только значимые результаты и ближайший шаг простым языком. Не журнал каждой правки.
- Не обновляй документацию автоматически вслед за кодом. Обновляй, только если её существующее описание стало неверным.
- Перед добавлением детали проверь: без неё читатель неправильно поймёт суть? Если нет — убери.

## Технические детали

- Для получения данных из TradingView используем пакет `@mathieuc/tradingview`.
- Для Fuzzy Dedupe и других операций нечёткого сравнения строк можно использовать `fuzzball`. Выбирай готовую функцию библиотеки, если она делает код проще и понятнее, чем собственная реализация.
- Для работы с датами и временем можно использовать `dayjs`. Выбирай его, если решение получается проще и понятнее, чем при использовании стандартных API JavaScript.
- Для типовых утилитарных операций можно использовать `radash`. Выбирай готовую утилиту библиотеки, если она делает код проще и понятнее, чем стандартные средства или собственная реализация.
- Для проверок типов используем функции из `src/helpers/utils.typed.js`. Прямую проверку оставляем только тогда, когда подходящей функции там нет, например для конкретного подкласса.
- Используется pnpm менеджер пакетов.

## Стиль кода

- Декларативный стиль. Красота, читаемость и компактность кода - приоритет! 
- Не переуслажняй код лишними проверками и функционалом. Проще - лучше.
- Не создаём `config.js` и именованные константы для фиксированных настроек: чисел, строк, путей, таймаутов, лимитов и списков. Хардкодим такие значения непосредственно в месте использования.
- Именованные импорты записываем в одну строку, если импорт остаётся достаточно коротким и читаемым. Переносим импорт на несколько строк только тогда, когда однострочная запись становится слишком длинной или ухудшает читаемость.

## Порядок работы

- Каждый шаг делаем отдельно, обсуждаем результат, потом двигаемся дальше.

- Не пишем код без явной команды пользователя. Сначала ТОЛЬКО обсуждаем структуру/логику по пунктам, и только после утверждения и явной команды (напр. "пиши код") приступаем к реализации.
- Используй компактную разметку markdown для ответов.

- Думай шаг за шагом!

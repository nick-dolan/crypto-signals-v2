# Crypto Signals v2

Система раннего предупреждения о сильных движениях криптовалют в ближайшие 4–12 часов. На основе рыночных признаков агент оценивает вероятность движения и выделяет наиболее интересные монеты. Результаты, графики, новости и публикации Twitter сохраняются в Parquet, открываются в веб-интерфейсе и скачиваются автономным HTML.

## Архив и сервер отчётов

Запускать из корня проекта, в разных терминалах:

```sh
pnpm install
pnpm server
```

Список отчётов: **http://127.0.0.1:3000/**. Сервер работает независимо от пайплайна:

```sh
pnpm all
```

**Шаг 13** больше не сохраняет HTML: собирает полный снимок и записывает его через `@duckdb/node-api` в `reports/<report-id>/`. Весь каталог `reports/` уже исключён из Git. Для нового снимка из согласованных промежуточных данных достаточно `pnpm exec node src/step13-report.js` — без повторных запросов к агенту и внешним источникам.

В каждом снимке четыре Parquet-файла с ZSTD:

- `report.parquet` — метаданные, версия архива, рыночный контекст, определения и описания монет;
- `coins.parquet` — кандидаты, типизированные признаки, оценки, объяснения и публикации;
- `history.parquet` — свечи, объём и OI основных кандидатов;
- `peer-radar.parquet` — радар соседей вместе с его сравнительными историями.

Вложенные данные хранятся типизированными `STRUCT`/`LIST`, а не одной JSON-строкой отчёта. Порядок массивов, пропуски, явные `null` и исходная точность JS-чисел сохраняются. Версия архива — в `data.manifest.version` файла `report.parquet`; схема полей записана в метаданных каждого файла. Схема определяется для каждого снимка, несовместимые числовые/текстовые значения не скрываются преобразованием в строку.

Пайплайн и сервер имеют отдельные экземпляры DuckDB в памяти; общего изменяемого файла `.duckdb` нет. Запись идёт в скрытый временный каталог рядом с архивом, после завершения он атомарно переименовывается в UUID отчёта. Сервер видит только опубликованные каталоги, а их файлы больше не изменяются. Не редактируйте содержимое опубликованных снимков вручную. После аварийного завершения могут остаться скрытые `.report-*` каталоги — они не показываются в списке.

Сервер читает только архив, не `tmp/` и не актуальные справочники. Список группируется по дате создания в UTC+3: недели с понедельника либо месяцы. На странице 30 отчётов; период может продолжаться на следующей странице. Курсорная пагинация не сдвигается при появлении новых отчётов. Кнопка «Обновить список» обнаруживает новые снимки без перезапуска сервера.

HTML/CSS/JS общие для просмотра и экспорта, сборки фронтенда и CDN нет:

- `src/reports/` — хранение и автономный HTML-экспорт;
- `src/server/` — независимый HTTP-сервер и JSON API;
- `src/web/` — список и существующий интерфейс отчёта.

Маршруты: `/`, `/reports/:id`, `/api/reports?group=week|month&limit=30&cursor=…`, `/api/reports/:id`, `/api/reports/:id/download`. Браузер получает обычный JSON, Parquet читает сервер. API списка возвращает `groups`, `total`, `nextCursor`; лимит — 1–100. Некорректные параметры дают 400, отсутствующие данные — 404, ошибка чтения архива — 500 с подробностями в журнале сервера.

**Скачать HTML** создаёт один файл со всеми сохранёнными данными, стилями, скриптами, графиками и лицензией. Он работает через `file://` без сервера и сети. Только `Update chart` делает публичные запросы к Binance; обновления остаются в памяти вкладки, архив и скачанный файл не меняются. HTML заранее не дублируется на диске.

Старые HTML/JSON-файлы сохранены, но не входят в новый список и автоматически не мигрируются. До первого нового снимка список пуст. Ошибка или отсутствие радара не мешает сохранению основного отчёта: причина входит в снимок.

По умолчанию сервер слушает только `127.0.0.1:3000`. Адрес и порт можно изменить переменными `HOST` и `PORT`, например `PORT=3001 pnpm server`. Авторизации нет: не публикуйте его в интернете без отдельной защиты доступа и HTTPS.

Проверки: `pnpm test`. Они используют временные архивы и не вызывают живые внешние API.

Дополнительная проверка в настоящем браузере: задайте `REPORT_BROWSER` (путь к исполняемому Chromium/Brave) и `REPORT_SMOKE_HTML` (путь к сохранённому HTML с кандидатами, свечами и непустым радаром), затем выполните `pnpm exec node --test tests/web-real-browser.test.js`. Без обеих переменных этот тест пропускается. Он создаёт временный профиль и архив, проверяет сайт и скачанный файл после остановки сервера, блокирует внешнюю сеть и удаляет временные файлы. Исходный HTML не изменяется.

## Справочник описаний монет

**Шаг 1.1** после отбора кандидатов дополняет `data/coin-descriptions.json` только новыми `baseCurrencyId`. Старые записи не изменяются и не удаляются, даже если монета вышла из топа. Когда новых монет нет, запросы и запись файла не выполняются.

Отдельный запуск по сохранённому результату шага 1:

```sh
pnpm exec node src/step1.1-coin-descriptions.js
```

Для каждой новой монеты агент через официальный GitHub Copilot SDK (GPT-5.6 Sol, medium) ищет источники инструментом `search_coin_sources` и читает выбранные страницы инструментом `read_coin_source`. Оба используют Tavily (`TAVILY_API_KEY` в `.env`); ключ не передаётся агенту. Приоритет — официальный сайт и документация. CoinGecko Demo API (`COINGECKO_API_KEY`) даёт вспомогательную привязку Binance USDT perpetual → проект и начальные ссылки; ошибка CoinGecko, отсутствие совпадения или пустое описание не мешают веб-исследованию. По одному тикеру проект не определяется: агент должен подтвердить его по прочитанным источникам.

На монету разрешены максимум **2 запроса поиска и 2 попытки чтения** (Tavily basic). Лимиты действуют и при параллельных вызовах инструментов, повторное успешное чтение использует кеш. Читать можно только публичные HTTP(S)-ссылки из результатов поиска или начальных данных. В справочник попадают 1–2 ссылки исключительно на успешно прочитанные страницы: агент выбирает выданные программой `sourceId`, а URL и `checkedAt` подставляет программа. Сниппеты и непрочитанные ссылки не считаются источниками; `checkedAt` означает время получения текста через Tavily, не дату обновления самой страницы.

Поисковые запросы и выбранные URL передаются Tavily, текст страниц — Copilot; это дополнительные расходы API/LLM только для новых монет. Старые записи, в том числе ранее составленные по CoinGecko, не переисследуются.

Без подтверждённой идентификации, прочитанного источника или корректного ответа агента запись не добавляется: выводится предупреждение, попытка повторяется при следующем запуске. Ошибка шага не мешает основному анализу. Повреждённый справочник не перезаписывается; успешное пополнение сохраняется атомарно. `coinCount` — размер всего справочника, `generatedAt` и `universe` — время последнего пополнения и использованный для него список, а не ограничение состава архива. Новые снимки отчётов включают актуальные описания; уже сохранённые снимки не меняются.

## Новости и Twitter в отчёте

Шаги 8–10 собирают и анализируют информационный фон для **топа агента и CoinGecko Trending среди монет основного отчёта**. Пересечения обрабатываются один раз; монеты вне предварительного отбора не добавляются. Сохраняются прежние лимиты: до трёх новостей и до двух страниц Twitter за последние сутки, один запрос агенту на монету.

Twitter ищем сразу в фиксированном 24-часовом окне: передаём `since_time` и `until_time` в Unix-секундах ([синтаксис TwitterAPI.io](https://docs.twitterapi.io/api-reference/endpoint/tweet_advanced_search)). Обе страницы используют одни границы, даже если загрузка началась позже среза. `until_time` исключает верхнюю границу, поэтому передаём следующую секунду, а локально сохраняем только публикации до `asOf` включительно. Пустая после фильтрации страница не останавливает загрузку, если есть курсор и API не сообщил об окончании; лимит остаётся две страницы. Это ограниченная выборка, не гарантия полного покрытия суток. Для обновления результатов после исправления поиска нужны шаги **9 → 10 → 13** — с повторной загрузкой Twitter и анализом агента.

Для trending-монет вне топа агент использует исходные аргументы за и против вместо отсутствующего общего объяснения. Их карточки тоже показывают информационный фон и источники; состав отчёта, ранги и вероятности движения не меняются. Дополнительные обращения к API и агенту нужны только для добавленных trending-монет.

В промежуточных результатах шагов 8–10 список называется `candidates`, а не `topCandidates`; топ шага 7 не менялся. Если сохранённые результаты обогащения ещё используют старый ключ `topCandidates`, нужно повторить шаги **8 → 9 → 10 → 13** по согласованным данным одного среза. Это заново загрузит публикации и вызовет агента.

В том же запросе шага 10 агент отдельно оценивает значимый инфоповод и сохраняет в JSON:

- `socialSignificant`: `true` — содержательное свежее событие с надёжным основанием или новая тема в независимых источниках; `false` — проверенный шум без убедительного инфоповода; `null` — данных недостаточно.
- `socialReason`: короткая причина на русском языке (до 300 символов); при неизвестной значимости допустим `null`.
- `socialSentiment`: при `true` — `positive`, `negative`, `mixed` или `neutral`; иначе `null`.

В списке монет только при `true` появляется SVG-мегафон: зелёный, красный, жёлтый или серый соответственно. В HTML `title` и доступном имени иконки — тональность и `socialReason`; причина также видна в информационном разделе карточки. Тональность относится к событию, а не к прогнозу цены. Популярность, CoinGecko Trending и число реакций сами по себе не дают пометку. При отсутствии публикаций значимость неизвестна, а не отрицательна; один недоступный источник не мешает оценке по другому.

Старые результаты с `candidates`, но без социальных полей, по-прежнему можно показать без пометок. Чтобы получить пометки по уже сохранённым публикациям, достаточно повторить **10 → 13**; это повторно вызовет агента, но не загрузку новостей и Twitter. Оценка относится к сохранённому окну публикаций, а не к моменту пересборки. Ответ агента теперь имеет `schemaVersion: 2`, результат шага 10 — `schemaVersion: 7`.

## Независимый радар соседей

- **Шаг 11** — по всем загруженным монетам ищет свежий рост прямых соседей и существенно более слабую реакцию связанной монеты.
- **Шаг 12** — отдельный агент объясняет только эти расхождения, без остальных групп признаков и без вероятностей. Промежуточный результат: `tmp/step12-peer-radar-analysis.json`, наблюдения `watch` / `limited` с точными фактами и оговорками. Выбранные агентом «Обратить внимание» (`watch`) идут первыми; остальные сохраняются.
- **Шаг 13** — полный снимок в Parquet для веб-отчёта и скачивания HTML с вкладками «Основной анализ» и «Радар соседей». У каждого кандидата радара — сравнительный график с его прямыми лидерами. Основной топ, оценки и графики не смешиваются с наблюдениями радара.

Отдельный запуск по сохранённым данным шагов 1–2 и справочнику `data/coin-peers.json`:

```sh
pnpm exec node src/step11-peer-radar.js && pnpm exec node src/step12-peer-radar-analysis.js
```

Шаг 11 не обращается к сети. Шаг 12 при непустом списке делает один дополнительный запрос через GitHub Copilot SDK (GPT-6-Astra, high), используя имеющуюся авторизацию; при пустом списке агент не вызывается. Сохраняются все наблюдения, а не обязательный топ-5. Это список для ручного решения, не рекомендация входа.

После готового шага 12 сохранить новый полный снимок можно без повторного обращения к агенту:

```sh
pnpm exec node src/step13-report.js
```

Шаг 13 читает `tmp/step12-peer-radar-analysis.json`. Добавляются все наблюдения, в том числе монеты вне основного shortlist. Нужен тот же часовой срез, что у основного анализа; при наличии скана шага 11 проверяется и его версия по времени создания. Отсутствующий, повреждённый или устаревший результат заменяется понятным предупреждением, основной отчёт остаётся доступен. Пустой завершённый скан показывается отдельно от недоступных данных. Отдельный архивный JSON радара больше не создаётся: его данные и графики входят в общий снимок шага 13.

Графики радара работают по сохранённой истории шага 2, без запросов к сети: периоды 1/3/7 дней, кандидат и все его лидеры на одном графике, цены в процентах от общего момента. Это визуальное сравнение, не ATR-критерий сигнала. Пропуски не заполняются, отсутствие общей начальной цены отключает только соответствующую линию. Сортировка `watch` первыми действует и для ранее сохранённого ответа агента — для новых вкладок и графиков достаточно повторить шаг 13.

`pnpm all` включает оба новых шага. Ошибка радара не блокирует сохранение основного снимка, но отмечается ненулевым кодом запуска. Подробные критерии и формат описаны в `docs/Признаки.md`.
